# 08 — Database layer

> Part of [`overview.md`](overview.md). Depends on: none. Owns: `packages/db/**` (schema, repositories, migrations, client, locks, tests, README). Only slice allowed to add a migration: **one**, `0044`.

Scale anchor for every cost below: prod had ~334k `usage_records` / ~360k `usage_contributions` (`docs/idea/08-observability.md:694`), i.e. a few thousand attempts/day. No live Postgres was available to this audit (dev DB on `:5433` not running), so **no `EXPLAIN` was run** — every planner statement is reasoned from index definitions and marked as such.

No non-negotiable violation found in this area: nothing in `packages/db` sits on the request-critical path except `findUsableByPrefix` on a key-cache miss (indexed, `api_keys_prefix_idx`), no credential column is logged or returned by a repository, retention cutoffs are all passed in.

## Findings

### 08.1 medium — No statement / lock / idle-in-transaction timeout on any pool; an abandoned usage summary keeps its connection
- **Kind:** db (reasoned, not reproduced)
- **Where:** `packages/db/src/client.ts:97-106`; `packages/db/src/migrate.ts:49-51`; `packages/db/src/repositories/usage-history-repository.ts:226-236`
- **Defect:** `postgres()` is built with no `connection: { statement_timeout, lock_timeout, idle_in_transaction_session_timeout }`, no repository takes an `AbortSignal`, and postgres.js queues statements with no acquire timeout — so nothing ever cancels a statement, and `grep -rn statement_timeout packages/db apps/api/src docs/idea` is empty.
- **Failure scenario:** `GET /api/admin/usage` opens one repeatable-read snapshot and runs ~23 statements on it (`apps/api/src/services/usage-read/summary.ts`); the doc measured 43.9 s post-fix / 351 s pre-fix at fixture scale. `SERVER_IDLE_TIMEOUT_SECONDS` (60) closes the socket, the transaction keeps running. Client retries → orphaned snapshots stack; at `DB_POOL_MAX` (10) every other user of the one main pool (`apps/api/src/main.ts:46`) queues forever: usage flush, scheduler sweeps, and the key-verification miss lookup (`composition/runtime-repositories.ts:57`) — a cold key's request hangs. Same gap at boot: `pg_advisory_lock` waits unbounded and silent behind a wedged replica, and a DDL waiting behind a long read queues every later query on that table.
- **Fix:** (a) `DatabaseOptions` gains `statementTimeoutSeconds`, `idleInTransactionTimeoutSeconds`, `lockTimeoutSeconds`, passed as postgres.js `connection` params; defaults in `DATABASE_POOL_DEFAULTS`, env `DB_STATEMENT_TIMEOUT_SECONDS` / `DB_IDLE_IN_TRANSACTION_TIMEOUT_SECONDS` / `DB_LOCK_TIMEOUT_SECONDS` in `apps/api/src/config/env-schema.ts` (slice owning config). (b) `withSnapshot` issues `set local statement_timeout` from an injected value below the HTTP idle bound. (c) `runMigrations` passes no statement timeout but a `lock_timeout`, and logs before blocking on the advisory lock. Update `docs/idea/09-deployment.md` env table and `docs/idea/08-observability.md:315`.
- **Test:** integration (`packages/db/test/integration/client.test.ts`): `select pg_sleep(2)` under a 1 s statement timeout rejects with `57014` and the pool serves the next query; a transaction left idle past the bound is terminated; migration with a held conflicting lock fails with `55P03` instead of hanging.

### 08.2 medium — Hourly `backfill` re-scans all of `usage_records` under the global history lock, ignoring the banked watermark
- **Kind:** perf (reasoned)
- **Where:** `packages/db/src/repositories/usage-history-maintenance.ts:33-45`, `:93-95`; caller `apps/api/src/scheduler/tasks/usage-rollup.ts:19`
- **Defect:** every `usage_rollup` tick starts with `cursor === undefined` and runs `select * from usage_records where not exists (… usage_contributions …) order by created_at, id limit N` from the top of the table, inside `lockUsageHistory` (`for update` on the single `usage_history_state` row); the watermark `coverage()` already trusts (`usage-history-repository.ts:90`) is not used as a floor.
- **Failure scenario:** steady state has zero unbanked rows, so the query cannot stop early: 90 days of raw rows × one PK probe each, hourly, while every usage flush (`usage-batch-mutation.ts:39`), retention batch and other replica's backfill waits on the same row lock. ~334k probes today (sub-second); linear in `RETENTION_USAGE_DAYS × traffic`, so 10× traffic is seconds of blocked usage writes per hour.
- **Fix:** read `state.bankedThroughAt/Id` from the lock result and, when both are set, add `(created_at, id) > (W.at, W.id) and created_at >= W.at` to the scan; keep the advance rule at `:93-95` (a floored sweep that ends short with no `legacy_overlap` still proves the invariant by induction). Keep one unfloored pass on a config cadence (`USAGE_BACKFILL_FULL_SCAN_HOURS`, default 24) because late pre-2.16 rows below W are otherwise never adopted — say so in `docs/idea/08-observability.md` "banked-through watermark".
- **Test:** `packages/db/test/integration/usage-history-watermark.test.ts`: failure case first — row inserted below W without a contribution is adopted by the full pass and not by the floored pass; floored pass over a banked table reads 0 `usage_records` rows before W (assert via `EXPLAIN (ANALYZE, BUFFERS)` buffers, as `bin/bench-usage` does).

### 08.3 medium — Request-id lookup casts the column, so neither arm can use `usage_records_correlation_idx`
- **Kind:** db
- **Where:** `packages/db/src/repositories/usage-recent-repository.ts:151-158` (comment `:138-149`), query `:123-133`
- **Defect:** `correlation_id::text = $1::text` is an expression on the column; the btree on `correlation_id` (uuid) cannot serve it, although the comment says the cast is "on the parameter side only, which leaves both index shapes untouched".
- **Failure scenario:** operator pastes a request id into `/api/admin/usage/recent?requestId=…`. One arm of the `OR` is unindexable, so no BitmapOr; the plan left is a backward walk of `usage_records_created_at_idx` filtering every row, and because a request id matches 1–3 rows the `LIMIT` is never reached: the whole retained table is read per lookup.
- **Fix:** branch in the repository: if the value parses as a UUID, emit `correlation_id = $1::uuid or (client_request_id is not null and client_request_id = $1)`; otherwise emit only the `client_request_id` arm. Fix the comment.
- **Test:** `packages/db/test/integration/usage-recent.test.ts`: `req-42` (non-uuid) still matches by client id and does not error; a uuid matches by correlation id; `EXPLAIN` of the uuid form names `usage_records_correlation_idx`.

### 08.4 medium — `tokensSince` joins `usage_records` on `account_id` with no index; the index test pins the opposite rule
- **Kind:** db (reasoned)
- **Where:** `packages/db/src/repositories/usage-tokens-since.ts:70-78`; `packages/db/migrations/0015_drop_unread_usage_indexes.sql`; `packages/db/test/unit/indexes.test.ts:58`
- **Defect:** 0015 dropped `(account_id, created_at)` because "accountId is a group-by dimension, never a leading predicate" (commit `8fe2eab`); `tokensSince` (per-account window gauges) and the #247 filters (`usage-read-repository.ts:52-56`) are exactly such predicates and arrived without the index.
- **Failure scenario:** every accounts list/get with a configured `windowTokenLimits` (`apps/api/src/services/accounts/availability.ts:282`) scans all accounts' rows since the oldest span start — a week of the whole table for a weekly window — once per (account, window) span or once hashed. 5 subs × 2 windows over ~26k rows/week today; grows with traffic on the console's most-polled page.
- **Fix:** 0044 adds `usage_records_account_created_idx (account_id, created_at) INCLUDE (tokens_in, tokens_out, cache_read_tokens, cache_write_tokens)` (index-only for the gauge). Net write cost on the hot insert path is neutral with 08.6 dropping one index from `usage_contributions`. Rewrite the test at `indexes.test.ts:58` to assert the new index and keep the absence of `api_key_created` / `session_key`.
- **Test:** unit `indexes.test.ts` shape assertion; integration `usage-tokens-since.test.ts` unchanged results.

### 08.5 medium — `coverage().legacy` scans every contribution in the window to prove there are none
- **Kind:** db (reasoned)
- **Where:** `packages/db/src/repositories/usage-history-repository.ts:89`; index `packages/db/src/schema/usage-contributions.ts:44-45`
- **Defect:** `exists(select 1 from usage_contributions where day between … and source <> 'live' and …)` has only `usage_contributions_day_idx` to ride, and `<>` is not indexable; on an install with no legacy rows the EXISTS can never stop early.
- **Failure scenario:** every summary load reads all receipts in the window through the day index to return `false`; for `lifetime` that is the entire table (retained `RETENTION_USAGE_DAILY_DAYS`, 730 d). `bin/bench-usage`'s lifetime leg judges only the `pending` check, so this is ungated.
- **Fix:** 0044 adds partial `usage_contributions_legacy_day_idx (day) WHERE source <> 'live'` — empty on a post-cutover install, so the probe is O(1). Add a buffers budget for the `legacy` arm to `bin/bench-usage` (owner: whoever holds `bin/`).
- **Test:** integration `usage-history-legacy.test.ts`: `EXPLAIN` of `coverage(lifetime)` names the partial index; flags unchanged for a legacy fixture.

### 08.6 medium — Dead indexes: one blocks HOT on a row updated every usage flush, one is a third index on the hottest insert table
- **Kind:** db
- **Where:** `packages/db/src/schema/accounts.ts:173-177`; `packages/db/src/repositories/account-repository.ts:189-204`; `packages/db/src/repositories/background-account-eligibility.ts:53`; `packages/db/src/schema/usage-contributions.ts:45`; `schema/quota-windows.ts:78`; `schema/model-catalog.ts:100`; `schema/audit-events.ts:36`
- **Defect:** seven indexes have no reader in `src/repositories/**` (the only place SQL lives): `accounts_last_used_at_idx` (its one stated reader orders `asc nulls first`, which a default `ASC NULLS LAST` btree cannot provide), `accounts_provider_idx`, `accounts_status_idx` (table is tens of rows), `usage_contributions_source_idx (source, id)` (every reader leads with `day` or the `(kind, id)` PK), `quota_windows_resets_at_idx`, `model_catalog_model_id_idx` (comment says the listing groups by model id; `model-catalog-repository.ts:96` orders by the PK), `audit_events_kind_created_idx`.
- **Failure scenario:** `markUsed` runs after every usage flush (`USAGE_FLUSH_INTERVAL_MS` 1 s, `apps/api/src/services/usage/fromEnv.ts:146`) and always changes `last_used_at`; an indexed-column change is never HOT, so each flush writes a new copy of every used account row (ciphertext + three jsonb columns) plus five index entries. `usage_contributions` takes two rows per request (attempt + terminal), each paying a third btree insert nothing reads.
- **Fix:** 0044 drops the seven; remove them from the schema files. In `markUsed` add `and (last_used_at is null or last_used_at < $at - $minInterval)` with the interval injected from config (consumers are the week-granular idle probe and a console timestamp) — say so in `docs/idea/02-domain-model.md` Account `lastUsedAt`.
- **Test:** `packages/db/test/integration/account-mark-used.test.ts`: failure case first — second stamp inside the interval updates 0 rows, a later one advances; `account-find-idle.test.ts` unchanged; `indexes.test.ts` asserts the seven are absent, naming why.

### 08.7 low — Open-run lookups scan the full run history on every scheduler tick
- **Kind:** db
- **Where:** `packages/db/src/repositories/scheduled-task-repository.ts:112-141`, `:193-201`; callers `apps/api/src/scheduler/orphan-runs.ts:24`, `runner.ts:102`, `services/settings/service.ts:160-165`
- **Defect:** `finished_at is null and started_at < cutoff` rides `(task, started_at)` / `(started_at)` and filters every row older than the cutoff — i.e. the whole 30-day table — before each tick of each of 14 tasks; the tasks screen issues 28 single-row queries.
- **Failure scenario:** tens of thousands of run rows read per tick to find zero open runs; `lastSuccess` walks back through a failure streak.
- **Fix:** 0044 adds partial `scheduled_task_runs_open_idx (task, started_at) WHERE finished_at IS NULL`. Add `latestPerTask()` (`select distinct on (task) … order by task, started_at desc`, plus the same filtered on `outcome = 'success'`) so the tasks screen is two statements.
- **Test:** `packages/db/test/integration/scheduler.test.ts`: `latestPerTask` equals per-task `lastRun`/`lastSuccess`, including a never-run task.

### 08.8 low — History retention sorts every expired receipt per batch
- **Kind:** perf
- **Where:** `packages/db/src/repositories/usage-history-maintenance.ts:155-158`
- **Defect:** `order by day, id, kind limit N` has only `(day)` to ride, so each batch sorts all rows below the horizon, under the history lock.
- **Failure scenario:** a day of D receipts leaves the window → D/1000 batches each sorting what remains: quadratic in D, blocking usage flushes meanwhile.
- **Fix:** `order by day` only (which rows of the oldest day go first is irrelevant).
- **Test:** `packages/db/test/integration/retention.test.ts`: backlog drains oldest day first, total deleted unchanged.

### 08.9 low — Over-fetch on list/admission reads
- **Kind:** db
- **Where:** `packages/db/src/repositories/api-key-repository.ts:169-178`; `usage-batch-mutation.ts:58-66`, `:87-98`; `api-key-tombstone-repository.ts:107`
- **Defect:** `keys.list` selects the AES ciphertext `value` for every key though the list view never shows it (`apps/api/src/services/keys/view.ts:8`); the admission duplicate check selects whole `usage_contributions` rows (incl. `payload` jsonb) and whole `usage_records` rows to read `id`/`source`/`payload_hash`; `listAll` loads every tombstone (731 d) on each usage read.
- **Failure scenario:** bytes and ciphertext carried into memory for no reader; grows with key count and redelivered batches.
- **Fix:** project columns: `list` without `value` (new `ApiKeyListRow` type; `findById` keeps it for reveal), admission check selects `{ id, source, payloadHash }`; cache tombstone labels in the label loader (owner: usage-read slice).
- **Test:** unit type test that `ApiKeyListRow` has no `value`; `api-key-attribution.test.ts` unchanged.

### 08.10 low — App-enforced invariants the schema does not back
- **Kind:** db (name-uniqueness history unverified)
- **Where:** `packages/db/src/schema/api-keys.ts:62-67`; `packages/db/src/repositories/admin-mutation-repository.ts:57-61`; `schema/quota-windows.ts:47`; `schema/usage-contributions.ts:31-35`; `schema/usage-aggregate-v2.ts:12`; `schema/usage-history-state.ts:8`
- **Defect:** key-name uniqueness is an advisory lock plus `findByName` (a seq scan — `name` has no index), while `pools.name` has `pools_name_key`; text-typed closed sets (`evidence_state`, contribution `kind`/`source`, `basis`) carry no CHECK unlike `account_recoveries.state`; `usage_history_state.revision` is never read or written.
- **Failure scenario:** any writer outside `AdminMutationRepository.run` (a script, `bin/admin`, a future path) can mint a duplicate name or an out-of-set value silently.
- **Fix:** before adding to 0044, run `select name, count(*) from api_keys group by 1 having count(*) > 1` on prod; if empty, add `uniqueIndex("api_keys_name_key")`. Add the three CHECKs `NOT VALID` then `VALIDATE` (cheap at this size). Drop `revision` only if no rollback image reads it (none does: column has no reader since 0030).
- **Test:** `packages/db/test/integration/api-key-attribution.test.ts`: duplicate name insert rejects with `23505`.

### 08.11 low — Migration guards are inconsistent with their own promise; every DDL lock is held to the end of one transaction
- **Kind:** docs / db
- **Where:** `packages/db/migrations/0041_sparkling_inhumans.sql`, `0043_fantastic_norrin_radd.sql`; comments in `0031`, `0037`, `0039`, `0040`, `0042`; `packages/db/src/migrate.ts:51`
- **Defect:** 0031–0042 state "`IF NOT EXISTS`, so a re-run is a no-op like every other one"; 0041/0043 are raw `ALTER TYPE … ADD VALUE` with no guard (as are most of 0000–0030). Re-runs are in fact skipped by drizzle's journal, not by the SQL, and drizzle applies all pending files in one transaction.
- **Failure scenario:** the "restore replayed over a newer schema" case 0039 guards against still fails on 0041/0043 with `42710`; an upgrade spanning several versions holds every `ACCESS EXCLUSIVE` from the first `ALTER` until the last statement commits.
- **Fix:** add `IF NOT EXISTS` to 0041/0043 only if the drift test tolerates it (drizzle hashes are not re-checked for applied files; confirm in `packages/db/test/integration/migrations.test.ts`), otherwise correct the comments and README to say the journal is the idempotency. Add a unit test that every `ADD VALUE` / `ADD COLUMN` / `CREATE INDEX` from 0044 on carries a guard. In 0044 order statements so `CREATE INDEX` (SHARE) precedes `DROP INDEX` (ACCESS EXCLUSIVE).
- **Test:** unit guard-lint over `migrations/*.sql` ≥ 0044.

## Checked, not a bug
- Key `lastUsedAt` is stamped only on a verifier cache miss, fire-and-forget (`apps/api/src/services/dataplane/auth/verifier.ts:185`, `last-used.ts:22`) — not an UPDATE per request.
- `usage_contributions` kept for `RETENTION_USAGE_DAILY_DAYS`: deliberate (`docs/idea/08-observability.md:1395`); receipts make replays idempotent after raw deletion.
- 14 facts scans per summary and the jsonb-typed receipts arm: measured and deliberately deferred, next lever named as `grouping sets` (`docs/idea/08-observability.md:343-348`). Not re-reported.
- Migration concurrency: `pg_advisory_lock` on a `max: 1` handle (`migrate.ts:41-49`); second replica waits, then finds nothing pending. Journal `when` values are strictly increasing through 0043, so drizzle's last-timestamp rule skips nothing.
- `ALTER TYPE … ADD VALUE` inside the migration transaction: no later file in the same batch uses a freshly added value.
- Session advisory locks live on a dedicated pool with `idle_timeout: 0, max_lifetime: 0` (`session-advisory-lock.ts:94-97`); a lost session aborts holders. No lock crosses pooled connections.
- Retention is bounded everywhere (`bounded-delete.ts:49`, `usage-history-maintenance.ts:121-224`); raw delete selects only banked rows, so the `usage_history_raw_delete_guard` trigger cannot starve a batch.
- FK columns without their own index (`oauth_states.account_id`, `pools.overflow_account_id`): both tables are tiny; parent delete cost is negligible. All other FK columns lead an index.
- `usage_records` token columns are int4 per attempt; all sums land in bigint/numeric (`usage-aggregate-v2.ts:13-21`). Cost is `numeric`, never float. Every timestamp is `with time zone`.
- BRIN on `usage_records.created_at`: rejected — retention and `recent` need ordered `LIMIT` scans.
- Scope/member replacement is delete+insert in one transaction (`api-key-repository.ts:244`, `pool-repository.ts:145`); `listTargetsForKeys` is batched, no N+1.
- Recovery/lifecycle repositories lock `accounts` then `account_recoveries` in one fixed order; no reversed pair found.
- No SQLite / `DATABASE_PATH` / single-file-DB leftover in `docs/`, `README.md`, `.env.example`, compose files.
